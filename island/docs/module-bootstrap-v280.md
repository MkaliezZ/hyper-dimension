# V280 — Recovering an unexecuted island module

The retained Intel macOS recovery-wait failure never reached the recovery controller: dynamic loading of `/src/app.js` failed and the screenshot contains only the static island HTML. The report and screenshot entries have verified CRCs; the entire artifact digest is not claimed verified. The original transport cause remains unknown and is separate from the broader ARM renderer stall.

The exact previous LAN bootstrap reproduces this state when the app module receives an explicit HTTP503: one request, zero app executions, no recovery entry. The LAN bootstrap now catches component loading errors. Only recognizable module-transport errors before the app entry executes may reload automatically, at most twice with a per-account/session counter. If counter storage is unavailable, the page offers an ordinary manual reload instead of looping. App initialization errors after entry and optional dock errors require an explicit reload; partially executed initialization is never automatically replayed. The current URL, selected appearance, account namespace and recovery-return nonce remain intact. No save, backup or pending journal is deleted.

Five real-DOM cases with minimal module stubs pass: both styles recover a single failed module request; permanent failure stops after two retries and its manual link actually recovers after the network returns; a post-entry runtime error is not replayed; unavailable session storage does not cause a reload loop. Isolated local progress and the existing recovery intent remain. Related recovery-navigation/intent controls pass. These are module-transport probes, not full island authority, real-model, human, physical-device or complete recovery acceptance. Full native re-entry and hosted verification after this patch remain pending. The independent V278 hour continues against its untouched frozen source and is not relabelled as a V280 execution.

The existing recovery-wait fixture also retains module status/content-type failures and a bounded loader-state observation. Its original fixtures, assertions and functional timeouts remain intact. Request headers, credentials and saved contents are not captured.
