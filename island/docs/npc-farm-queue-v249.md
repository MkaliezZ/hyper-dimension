# V249 · 农活与备份的排队边界

## 问题

V247 实际一小时运行完成，两套画风的性能、画面帧间隔与空浏览器恢复检查通过，但折纸岛出现一次 NPC 收获请求被服务端以 `farm_stage` 拒绝，因此整轮功能检查未通过。V248 没有修改这一部分，后续一小时及从零进度续做尚未启动，先保留现场修复。

居民开始农活时已有一次田地检查，但请求等待其他作业回执期间，田地可能已经变化。现在新 NPC 农活与玩家农活一样，在共享队列和保存前置完成后、写入新请求记录之前，再检查已确认的田地阶段和作物。未提交的过期动作会交回居民重新安排；真正不确定的原编号请求仍走原恢复流程。

## 验证

- 两套画风分别延迟一笔真实浇水完成答复和一笔真实收获完成答复，后面排入旧 NPC 动作：修改前4例都产生服务端阶段错误，修改后4例都停止旧请求，未锁界面、未生成多余作物或完成回执。
- 后续有效 NPC 浇水能够取得实际许可，并正常取消、释放预留；玩家原有2例和已确认成熟度组件2例通过。
- 相关农田规则19项、完整必需规则1300项通过；服务端阶段、成熟时间、种子、工具与唯一结算校验没有放松。详见[证明摘要](verification/v249/npc-farm-queue.json)。

## 备份与 macOS 检查

完整规则检查另外暴露了备份竞争：保存检查点完成后，备份本身还在编码或写盘，后续作业可能先更新版本。延迟实际备份的确定性用例保留原失败；现在整个备份请求占据同一队列位置，并让同时发生的自动保存等待。新界面修改在备份后保存，不会丢弃，也不混入先前请求的快照。相关备份与共创目录本地25项、原生签名导入／历史恢复6例通过。

[原 macOS Intel 检查](https://github.com/MkaliezZ/hyper-dimension/actions/runs/39001947046/job/117306549514)有两个测试把系统临时目录的符号链接别名直接交给受保护数据服务。测试现先取得临时目录的真实路径，再创建隔离目录；服务端拒绝符号链接的数据保护规则保留。本地通过不代表新的托管 macOS 检查已经成功，后者另行跟踪。

上述原生测试有明确的工具与田地阶段夹具，不是从零成长、真人或新一小时验收。原一小时仍标记失败；新交付包与其连续运行结果另行记录。没有更改收益、模型频率、用户存档或配置。
