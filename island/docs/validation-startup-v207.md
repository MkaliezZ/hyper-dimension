# V207 · 启动恢复与验收时序

## 实际失败

- V206 提交 `4fe7e0881cc0e70f1d250bacb8daad96155ce8a8` 的 Windows 原生玩法任务 `116844759053`：恢复测试看到制作卡片后立即检查按钮，但后续居民控制器仍在核对回执。失败截图随后已显示正确的“继续 / 取消”入口。
- 在隔离测试岛扣住真实居民取消响应，旧的检查顺序确定性复现 `true !== false`，启动阶段为 `controller-5`。这与 V205 旧页面重新提交过时物资的产品缺陷不同；后者仍由 V206 的客户端隔离和回归覆盖。
- V205 的 macOS 14 任务 `116835768525` 在背包点击灯笼时超时，尚未进入检查点测试。原测试仅等待经营控制器，早于全部启动恢复完成。该点击超时在本机正常速度及 4 倍 CPU 限速下均未复现，因此不将其记录为已证明修复的 macOS 产品问题。

## 调整

恢复测试现在扣住一次真实启动回执，验证启动尚未完成，释放同一响应，并等待全部控制器恢复完成后检查原有按钮断言。检查点测试同样等待完整启动。没有增加原有超时时间，也没有使用强制点击、跳过原生输入、减少关卡或放宽结果断言。

保留取消仅一次、材料不丢失、丢失响应重放、旧页面检查点隔离、三次刷新无重复提示，以及检查点未确认时禁止重开、确认后新票据重开的检查。工作流额外保留检查点报告和截图；失败诊断补充启动阶段、弹窗标题、目标坐标、滚动位置和 inert 状态。

## 本机证据与边界

Windows 隔离 Chromium 的两画风恢复用例、两画风原生检查点用例及 5 项相关单元测试通过。旧检查顺序在持有回执时明确失败；正确等待完整恢复后，相同断言通过。用户存档、配置、浏览器和运行服务未被修改，没有调用模型。

游戏运行时代码和 V206 交付压缩包保持原样。本次修改为测试生命周期同步、失败诊断及产物保留；托管 Windows/macOS 的恢复结果等待新提交运行确认。它不构成真人或物理多设备验收。
