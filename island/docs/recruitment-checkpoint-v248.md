# V248 · 后台结算与用户操作排队

## 发现与修复

[原 Windows 检查](https://github.com/MkaliezZ/hyper-dimension/actions/runs/38997541832/job/117293284626)中，签名导入／历史恢复步骤已经通过，随后招聘取消失败。隔离截图显示：共享作业正在确认时，取消入口尝试直接保存，被“作业结算待核对”拒绝，取消请求没有发出。

现在外部保存检查点进入与已提交作业相同的队列，等待其回执，再允许后续操作。招聘确认、取消、档案／政策修改、手动保存与备份、游客入港前确认，以及管家等页面的保存前置使用此顺序。真正丢失响应的作业仍保留原编号和恢复入口；没有跳过服务端版本校验、清空待核对记录或提前释放报酬。

## 验证范围

- 延迟真实共享请求的200答复，在两套画风各复现一次取消失败；修复后4个招聘错误场景通过，原编号重试、状态身份匹配、单次取消和8币预留释放保留。
- 新增3项队列检查：已接受作业与后续操作之间保存；不确定结果必须原编号重放；备份包含先前已接受的修改并排除后续排队项目。完整必需规则1298项通过。
- 双画风6个原生签名导入／历史恢复，以及2个零开局商品制作到游客实际购买流程通过。详见[证明摘要](verification/v248/recruitment-checkpoint.json)。
