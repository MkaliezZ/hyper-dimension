# V218 · Windows 存档互斥获取

V217 的 Windows 顺序分工中，折纸案例已完成原预算，像素案例出现一次 EPERM503，随后作业停在待确认状态。该次响应只记录了错误代码，尚不能确认原始文件系统调用与路径；日志和隔离产物保留，不将推测当作完整根因。

静态检查发现，主存档的 write.lock 仍直接调用 open(...,'wx')，未使用项目已有的 openExclusiveFile 短暂占用处理。已在真实 createSaveStore 事务中复现该缺口：注入短暂 EPERM、EACCES 或 EBUSY 时，旧代码立即失败。

现在主存档复用现有有界获取函数。只重试取得互斥之前的文件打开，仍使用 wx 与原权限；不会删除别人的锁、跳过所有权检查、重复执行已开始的资源事务或吞掉永久权限错误。持续失败仍抛错，原始存档字节与资源保持。

四个新用例及关联原子写入/互斥规则通过；Windows 实际浏览器双画风案例在采集完成阶段注入三次 EPERM，界面无需进入人工恢复，采集只产生一笔回执，并能在空浏览器恢复。相同请求重放唯一性由真实存档级用例另行验证，浏览器案例不冒称执行了该步骤。初版浏览器夹具的请求选择器和完成状态等待错误已保留在私有诊断中；修正后保留真实错误注入和全部结果断言。

原生分工诊断补充实际错误文本、操作类型，方便区分后续其他 I/O 位置。原第一项120秒、余下共享240秒工作时间、数量、依赖、唯一回执和刷新检查不变。新增 Windows 页面故障测试保留平台判断，不把其跳过结果称为 Mac 测试。
