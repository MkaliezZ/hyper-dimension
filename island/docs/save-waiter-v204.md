# 等候保存与制作请求的版本顺序

Windows 原生玩法检查停在折纸版的肥料制作入口。诊断显示客户端处于 `save_conflict`，尚未取得制作关卡；此前的像素种植、施肥、完整生长和收获流程已通过。

问题位于保存完成的接续顺序：制作等待一笔保存，另一个已经排队的保存也在等待同一笔请求。保存结束后，后者可能先接续提交；制作从自己的外层等待恢复时，却直接捕获了旧版本。

操作现在会继续等待已经接续执行的保存完成，再保留发送顺序并捕获已确认版本。服务端版本校验、物资预留、回执去重和真正并发冲突的恢复规则保持原值。

## 复现与检查

- `tests/v204-save-waiter.test.mjs` 确定地安排两笔保存与一笔制作，旧实现触发版本冲突，修正后按顺序提交，并保留期间的导航修改。
- `tests/v204-save-waiter-browser.mjs` 使用实际浏览器、IndexedDB 后台暂存和独立 HTTP 服务。不可变 V203 在两种画风均复现同一冲突；修正后各开始一项真实肥料制作再取消，物料和金币恢复，唯一取消回执保留。
- 原有 `tests/v159-soil-care-browser.mjs` 继续检查实际推匣制作肥料、播种、浇水、施肥、完整生长、收获和刷新；追加保存请求版本与回包顺序诊断，便于定位后续失败。

这些检查只使用虚构的隔离存档，模型请求关闭。浏览器保存顺序检查不等同于游戏手感、真人或实体多设备验收。
