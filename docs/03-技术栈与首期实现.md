# 03｜技术栈与首期实现

更新：2026-09-26。本文按公开仓库的实际开发状态，区分可运行的 Web 视觉 DEMO、待建的岛主工作台和后续 Agent 交互能力；首期先验证资料入岛与教培场景的业务闭环。协议与代码可逐步开源，以托管服务和岛屿运营验证差异化。设备具体型号、接口与部署规模在实物验收后固定。

## 1. 一句话结论

目标架构是“全体用户 Agent 云端运行 + 岛主 Agent 内置受限管家能力 + 轻量审计入口 + PostgreSQL 业务数据 + 集群共享英语教材检索服务 + 对外 A2A 接口”。平台不为每次来访运行额外的统一管家模型。本仓库提供可运行的 Web 小岛视觉 DEMO，后续在现有页面与 2D/3D 建岛包之上接入岛主 Agent 和必要的业务后端。首个教培样板先验证“采集资料 → 岛主确认 → 发布到岛屿 → 访客互动 → 岛主跟进”；A2A 属于真实访客 Agent 接入阶段，不把它写成现有 prototype 已具备的能力。Hyper Dimension 自己定义资料来源、访问、授权、发布、审计和提醒规则。[A2A 规范](https://a2a-protocol.org/latest/specification/)

### 当前公开仓库的实现边界

本仓库包含可运行的 Astro 2D 小岛视觉 DEMO、本地教师英语测评与档案切片、MCP 工具和版本化业务协议。当前没有生产身份网关、共享教材检索服务或公开 A2A 端点。视觉 DEMO 与本地模拟数据不代表生产服务已完成。

## 2. 按开发依赖顺序排列的具体技术栈

以下顺序依据首期教培样板的开发依赖：世界观由**本体数据、互动逻辑、空间呈现**组成；1.0 聚焦教培老师建岛、家长或学生登岛、两三套与现实业务关联的互动逻辑。硬件控制终端属于 1.0 验证范围；学生独立副岛、竞赛副本和复杂玩法不进入第一个纵向切片。当前顺序是开发依赖，不表示每一步必须串行：ESP32-S3 板卡外设验证可与云端后端开发并行。

| 顺序与验收节点 | 具体技术栈 | 本阶段要交付的能力 | 进入下一步的条件 |
| --- | --- | --- | --- |
| **0. 锁定样板与三层契约** | 现有 [Astro](https://astro.build/) 源码与 2D/3D 建岛包；用 JSON Schema、FastAPI/Pydantic 的 OpenAPI 描述数据和 API；教育操作另用版本化命令 Schema 固定 MCP/A2A 共用语义 | 选定一位教培老师、一个主要经营动作和一册学校实际使用的英语教材；核对出版社、系列、学制、年级、册次、修订年/印次和教材来源；定义资料来源与版本、岛屿/物件 ID、可见范围、互动动作、空间清单和事件 ID。先找回可编辑源码与发布流程，避免修改线上构建产物 | 同一份已审核内容可被 2D/3D 页面引用；主要访客动线和验收样例明确 |
| **1. 云端业务底座** | [FastAPI](https://github.com/fastapi/fastapi) + [PostgreSQL](https://www.postgresql.org/docs/current/)；现有 nginx/HTTPS 反向代理；新增服务用 [Docker Compose](https://docs.docker.com/compose/gettingstarted/) 部署；数据库任务表 + worker | 建立用户、岛屿、资料、授权、发布、访问、交互与审计数据模型；实现岛屿身份隔离、基本认证、事件写入、幂等和持久任务。业务后端与数据库部署在静态站点机之外 | 网页模拟请求可可靠写入来源和审计事件；跨岛读取被拒绝，失败任务可追踪 |
| **1A. 集群共享英语教材目录** | PostgreSQL 教材版次/章节/权利元数据；按哈希寻址的受控对象存储；教材版本 Schema 与教师班级绑定 API | 每套集群建立一个逻辑共享目录，按 edition_ref 标识具体课本。教师、班级和学生只保存版次、章节和学校进度引用，不复制 PDF；同一版教材可供多个已授权教师 Agent 调用。对本地 258 份 PDF 核对来源、版次、哈希、页数和可用权利，未核准者只能进入研究目录 | 两名模拟教师引用同一版教材而不产生两份原书；版次不唯一时要求教师确认，权利未核准时不能返回正文 |
| **2. 资料入岛与发布** | FastAPI 上传/审核 API；已获准教材的 OCR/分段 worker + PostgreSQL 全文检索 + [pgvector](https://github.com/pgvector/pgvector) 共享向量索引；检索前锁定 edition_ref、权利范围和复核状态，检索后核对原书哈希与页码；开发期文件目录保存其他媒体，正式多实例部署再评估 S3 兼容存储如 [SeaweedFS](https://github.com/seaweedfs/seaweedfs)；[SQLAdmin](https://github.com/smithyhq/sqladmin) 仅供内部试点审核；可选独立 worker 接入 [faster-whisper](https://github.com/SYSTRAN/faster-whisper)、[PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) | 网页先模拟录音、拍照和按键采集；保存原件与来源，生成待审核草稿；岛主确认后生成公开内容版本与空间清单，支持拒绝和撤回。教材库仅对权利和内容审核通过的分段建立检索索引；抽样页无文本的扫描件先 OCR 和抽检，不靠向量相似度猜测正文。设备资料转写/识字不是首个发布闭环的前置条件 | 一份资料完成“采集 → 审核 → 发布或拒绝”，公开岛屿只读取获准版本；教材检索能返回具体版次/页码/来源状态，错误版次或无权正文被拒绝 |
| **3. 岛主云端 Agent 与受限管家能力** | 云端 Agent 运行适配层 + 模型提供方接口；[MCP 官方 Python SDK](https://github.com/modelcontextprotocol/python-sdk) 暴露教师 Agent 白名单工具，FastAPI 与 MCP 共用同一业务服务；PostgreSQL 会话/任务与用量记录；按需引入 [Keycloak](https://www.keycloak.org/) 承担 OIDC/OAuth2，不与当前静态站点同机部署 | 每位岛主 Agent 只读本岛获准资料；教师 Agent 通过 MCP 检索共享教材目录、章节和证据引用，按受限管家身份回答或请求岛主本人审批；服务端控制工具、租户隔离、速率与模型额度。不得把桌面版 Codex、WorkBuddy 或 dsh 直接当作可托管的云端 Agent | 经模拟访客提问能正确回答、拒绝或转审批；两名教师 Agent 可复用同一教材索引且不混淆不同印次；用量归属和故障状态可查 |
| **4. Web 建岛、登岛与经营闭环** | 沿用 Astro 页面和现有 2D/3D 素材；需要场景交互时继续用 [Three.js](https://threejs.org/docs/)；页面经 FastAPI 调用第 1—3 步的服务；worker 生成收件箱与提醒 | 页面从空间清单加载岛屿；实现登岛、探索物件、与管家交谈及一个留资/报名动作等两三套基础互动；记录 visit、interaction、物件事件与提醒来源。复杂游戏引擎暂不引入 | 家长或学生从登岛到目标动作可完成，岛主能看到可追溯的访问与跟进记录 |
| **5. ESP32-S3 控制终端联调** | [ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/) + HTTPS 设备 API；依据板卡实物适配录音、拍照、屏显、触控或按键；[FoloToy AI Passport](https://github.com/FoloToy/ai-passport) 仅作交互与固件分层参考 | 与网页模拟输入复用同一采集、回执和审计流程；完成设备绑定/撤销、capture_id、上传重试与幂等。设备不运行岛主 Agent，也不长期保存用户资料；具体外设先按实物核验 | 实物和网页模拟输入产生相同业务结果，重复上传不重复发布；设备离线不阻断已获准网页 |
| **6. 外部访客 Agent 的 A2A 接入** | [A2A 官方 Python SDK](https://github.com/a2aproject/a2a-python) + Agent Card；FastAPI 审计入口 | 让访客云端 Agent 经平台入口调用岛主云端 Agent；按 interaction_id 关联 A2A Task、权限决定、答复和审计。不把页面点击、设备上传或内部任务伪装成 A2A | 真实访客 Agent 可完成一次受控访问，入口内请求与回复可对账 |
| **7. 多端与二期交互扩展** | Web 闭环后复用 API 建 [Taro + React + TypeScript](https://docs.taro.zone/docs/react-overall) 微信小程序；二期再以现有 Web/Three.js 为基线比较 Godot、Unity Web 等引擎 | 扩展移动入口、成员/副岛与成长机制；以同一空间清单和事件契约驱动新呈现方式，避免重写业务后端 | 仅在 1.0 样板的使用、运营与成本指标成立后启动 |

### 2.1 首期英语教材共享检索服务

这是一套供已认证教师 Agent 共用的**集群级资料服务**，不是向互联网匿名开放的数据库，也不是把整本 PDF 塞进模型上下文。现有本地原书为 258 份 PDF、25,584,336,094 字节（约 25.58 GB）；44 份的抽样页没有可提取文本。当前只完成文件完整性和部分目录/正文核查，尚未证明逐册最新、OCR 完整或可商业复用。完整设计见[共享教材库与向量索引](curriculum/shared-textbook-catalog-v0.1.md)。

| 层 | 首期选型与数据 | 访问边界 |
| --- | --- | --- |
| 原书对象 | 受控对象存储按 SHA-256 去重，按集群共享；副本、备份和跨集群复制按恢复目标配置 | 原书不进 Git、教师档案或 Agent 提示词；教师 Agent 无对象路径或整本下载权限 |
| 版本与证据目录 | PostgreSQL 记录 edition_ref、出版社/系列/学制/年级/册次/修订年/印次、ISBN、asset_hash、section_ref、页码、内容复核与权利状态 | 先确认学校使用的具体版次；目录级记录不能冒充正文级证据 |
| 检索索引 | 已获准且复核的分段建立全文索引和 pgvector 向量；记录 chunk_ref、embedding_model/version 与原页码 | 先按 edition_ref、权利范围和章节过滤，再混合检索，最后回查原书哈希与页码；语义相近不能跨版本替代 |
| 教师绑定与产出 | teacher_textbook_binding、学生档案、题包和报告只保存 edition_ref、section_ref、授课进度与检索证据版本 | 多教师共用一套索引；历史报告固定原版本，换书或重建向量不改写历史依据 |

教师 Agent 的 MCP 工具依次提供 resolve_textbook_edition、list_textbook_sections、search_textbook_evidence；bind_class_textbook 仅在教师确认具体版本后执行并留审计。A2A 只传教材和证据引用，不传原书文件。教材检索失败、页码不符、OCR 质量不足、版次不唯一或权利范围不足时返回明确状态并要求核对，不能让 Agent 自行补全课文。

实施门槛依次为：来源与权利核准 → 文件哈希和页数校验 → 版次与学校用书确认 → OCR/人工抽检 → 章节和页码复核 → 全文索引 → 向量索引与检索质量验收 → 教师 MCP 接入。教材原书的本地研究持有不自动授予集群多教师使用或在线传播权；权利未核准时，首期仍可先上线版本元数据和原创教学摘要，不将 PDF 全文提供给 Agent。[国家版权局《著作权法》](https://www.ncac.gov.cn/xxfb/flfg/flfg_532/202103/t20210309_50530.html)

贯穿第 1—6 步的技术要求：用 [OpenTelemetry](https://opentelemetry.io/docs/languages/python/getting-started/) 做技术追踪，用独立事件表做业务审计；为数据库与素材做备份恢复；从 Agent 接入时执行租户隔离、模型用量额度和成本归属。Keycloak、SeaweedFS、识别模型及 React-admin 都有明确触发条件，不作为启动项目时必须安装的全套组件。静态站点、业务数据库、Agent 推理和教材索引按资源需求分别部署，不把所有服务强制放在一台机器。

## 3. 三方链路与协议边界

~~~text
访客本人 ── Web/小程序 API ──┐
                            ├─ 平台审计入口 ── 岛主云端 Agent（受限管家能力）
访客云端 Agent ── A2A ─────┘                     │
                                               └─ 必要时请求岛主本人审批
~~~

页面点击是人机交互；只有访客云端 Agent 真正发起协议请求才是 A2A。岛主 Agent 对外以管家身份提供受限能力，由平台入口强制校验身份、额度、资料权限并记录消息和结果。通常只有访客 Agent 到岛主 Agent 的一段 A2A。平台不额外运行统一管家模型，不使用本地连接器或反向通道。

所有平台认可的交互经审计入口；MCP 提供结构化、可校验的 Agent 工具，但工具说明和 Skill 均不能替代服务端授权、幂等与审计。英语测评 Skill 保留命题方法，档案、出题、审批和发布由业务服务执行。平台用 interaction_id 关联页面会话、A2A Task、策略决定、批准与提醒。岛主 Agent 若再委托另一云端 Agent，分别记录两个 Task ID。A2A Task 历史不能代替业务审计。[A2A 规范](https://a2a-protocol.org/latest/specification/)

## 4. 必须自行开发的 Hyper Dimension 业务模块

1. 岛屿与资料管理：岛主通过网页、设备或授权 Agent 提交录音、照片、作品与案例；保存原始来源、采集主体、用途、授权范围和版本。资料分为公开展示、交互中可回答、仅管家、仅岛主等类别；素材包提供统一配置格式。
2. 管家策略：岛主云端 Agent 的受限能力先经服务端判定访客身份、资料可见性和岛主授权范围，再回答、拒绝或请求岛主本人确认。外部输入和访客 Agent 指令一律作为不可信内容处理。
3. 交互与审批编排：任务状态、超时、云端故障排队、重试、幂等、人工审批和回复归属。故障时持久化任务，恢复后按状态继续；有副作用的操作使用幂等键。
4. 云端 Agent 运行适配：只接入能在云端稳定运行、具备可授权调用接口的 Agent；以隔离身份、工具白名单、健康检查和用量统计管理。Codex、WorkBuddy、dsh 等具体产品须逐一验证其云端运行和自动化接口，不能把桌面版等同于云端服务。
5. 审计与提醒：访问打开、点击管家、发送消息、策略判断、岛主审批、最终答复均生成事件。保存事件 ID、时间、actor、island_id、interaction_id、相关 task_id、结果和内容引用。敏感正文单独加密保存并按保留期清理；审计表限制修改权限。每次转交和提醒保留来源事件 ID。
6. 岛主可控性：公开范围、是否允许 Agent 代访、管家能力边界、模型用量额度、安静时段、通知频率和数据保留期，都由岛主配置。
7. 岛主工作台与发布流：实现“已采集 → 处理中 → 待岛主确认 → 已发布／已拒绝”的状态机；转写、识字与 Agent 整理只生成草稿。岛主确认后生成获准展示的内容版本与空间清单，供 2D、3D 和后续引擎读取；发布、撤回和修改均写入审计。设备采集与访客互动分别使用独立的事件类型，不让设备直接改写公开页面。
8. 共享教材治理：管理原书权利、版次、哈希、OCR、章节与页码复核、全文/向量索引版本、教师用书绑定和 MCP 检索授权。错误版次或证据不足时停止教材对齐出题；学生档案、教师 Agent 和公开岛屿均不保存整本 PDF。

推荐 PostgreSQL 表至少包括 users、islands、devices、device_bindings、source_assets、content_items、content_revisions、publication_decisions、scene_objects、agent_endpoints、visits、interactions、agent_tasks、task_deliveries、audit_events、reminder_jobs。英语教育另设集群级 textbook_editions、textbook_assets、textbook_sections、textbook_chunks 与 teacher_textbook_bindings：多个教师 Agent 复用同一教材索引，学生档案只存版本/章节/进度引用，不复制原书。设备事件携带 device_id、capture_id 与幂等键；原始资料、处理草稿和公开版本分离。业务事务同时写状态和待投递记录，worker 再投递，以降低“记录成功但任务丢失”的风险。技术追踪用于排障，业务审计用于解释“谁在什么时候访问并交换了什么信息”，两者分开。

## 5. 可延后引入的开源组件

| 需求出现时 | 候选 | 为什么暂缓 |
| --- | --- | --- |

| 任务量增加、跨多台网关可靠传递 | [NATS JetStream](https://docs.nats.io/concepts/jetstream) | 单机/小规模先用 PostgreSQL 任务表，减少运行组件 |
| 长期审批和多步骤工作流非常复杂 | [Temporal](https://github.com/temporalio/temporal) | 首期状态机 + 数据库队列足以验证流程 |
| 岛屿、资料、代理权限关系复杂 | [OpenFGA](https://openfga.dev/) | 首期策略可在业务服务内实现，先确定权限语义 |
| 希望平台自托管模型推理 | [vLLM](https://docs.vllm.ai/en/latest/serving/openai_compatible_server/) | 需要根据模型、硬件、成本和效果单独选型；推理框架开源不等于模型许可自动满足产品需求 |
| 用户拥有独立 Solid Pod、要求跨应用数据授权 | [Solid SAI 草案](https://solidproject.org/TR/sai#agents) | 当前核心是 Agent 通信和平台内资料权限，SAI 不是必需依赖 |
| 设备规模需要持续双向消息、主题订阅与断线重投 | [Eclipse Mosquitto](https://github.com/eclipse-mosquitto/mosquitto) | 单台/少量设备先用 HTTPS 请求与回执，暂不增加 MQTT Broker |

## 6. 现有原型与后端增量部署

现有 Astro 静态页面可继续由 nginx/HTTPS 提供服务。FastAPI 业务与审计服务、岛主云端 Agent、PostgreSQL 和教材索引部署在具备相应资源的独立运行环境，通过受控 API 对接静态页面。Docker Compose 可用于新增后端组件，但不是改造现有静态站点的前提。媒体资产应封装存储接口；集群级教材原书和索引由独立的受控存储/数据库承载，不复制到现有静态站点机，也不按每位教师部署一份；备份、冗余与跨集群复制按恢复目标配置，容量需计入 OCR、向量索引和副本。正式环境为数据库与素材设置备份和恢复演练。[Docker Compose 快速入门](https://docs.docker.com/compose/gettingstarted/)

每个用户的岛屿、管家人格和授权策略是逻辑隔离配置；无需给每位用户部署一整套 API 和数据库。所有用户 Agent 在云端运行，运行时按用户/岛屿隔离身份、资料、工具和预算。对处理私密资料的 worker 设置每任务的岛屿身份与数据访问范围。

岛主 Agent 的云端运行环境应有健康检查、可追踪的任务状态和故障恢复。平台需核算云端基础设施、推理、存储与审计成本；推理按用户归属记录，配额与计费在请求入口强制执行。设备离线时，已获准的网页入口继续工作，不能把设备在线误设为小岛可访问的前提。

### 首期工作台与硬件边界

工作台是现有 FastAPI 后端中的业务模块及岛主操作界面，不另建一套业务真相源。最小流程为“设备或网页采集 → 保存原始资料及来源 → 可选转写/识字和 Agent 整理 → 岛主审核 → 发布获准版本到岛屿 → 记录访客互动 → 岛主收件箱”。自动处理结果只是草稿；尤其涉及学生作品、照片或学习记录时，不因采集成功而自动公开。2D/3D 页面读取同一份已发布空间清单和内容版本，不能直接读取未审核原件。

ESP32-S3 作为当前硬件开发套件方向。先定义与具体板卡无关的设备协议：绑定与撤销、设备身份、capture_id、媒体上传或操作事件、接收回执、重试和幂等。首期优先 HTTPS；当设备规模和持续双向消息要求明确后再评估 MQTT。录音、拍照、屏显、触控和按键以实际套件外设为准；“不做本地存储”应解释为不长期保存用户资料，采集与断网重试所需的临时缓冲须有清理规则。FoloToy AI Passport 的公开方案基于 ESP32-C3、无 PSRAM，整机规格未列摄像头或触屏；若首期只需按键、录音和屏显，C3 可用于验证，但不能直接套用其板级支持包到 S3 套件。[FoloToy 规格](https://github.com/FoloToy/ai-passport/blob/main/docs/hardware-design/specifications.md)

## 7. 素材包与交付次序

**首期实现唯一开发目录**为本仓库根目录；公开代码仓库为 [MkaliezZ/hyper-dimension](https://github.com/MkaliezZ/hyper-dimension)，main 分支采用 MIT 许可证。后续首期后端、协议契约、测试、迁移与受保护页面均在该目录迭代；每次验证后检查提交内容、commit 并 push。2D/3D 本地演示和建岛包仍是素材与展示参考，不作为另一套业务后端开发目录。公开仓库只纳入模拟资料和有授权的素材。

现有 2D/3D 建岛新手包已能在开发机本地生成和预览展示页面，继续作为渲染与素材交付基线；这只是构建验收步骤，正式运行的用户 Agent 全部在云端。新手包尚不包含云端业务后端。后续包内应提供稳定的空间配置和内容 API 契约，仍将用户资料与平台代码分离，确保升级不覆盖用户自定义岛屿。设备凭据、服务端密钥和真实客户资料不得打进通用新手包。Web/小程序模板、素材授权说明、Agent 接入说明、部署文件、升级与回滚说明按实际阶段补齐。

建议按以下可验收顺序推进。首个样板聚焦一位教培老师、一种主要访客任务和一个主要经营动作；这一顺序与第 2 节的技术栈节点一一对应。英语教师版的课程与多教材设计见[英语能力主线](curriculum/curriculum-architecture-v0.1.md)：

1. 固定可编辑的 Astro 源码与发布流程；定义资料本体、两三种建岛/登岛互动动作、空间清单和事件契约。并行核验 ESP32-S3 开发套件的实际录音、拍照、屏显、触控、按键与内存配置。
2. 部署独立的 FastAPI + PostgreSQL 业务底座，完成岛屿身份、资料来源、授权、审计与持久任务；同步建立集群级教材版本目录。先让教师核对并绑定 edition_ref、授课章节和进度，验证两个教师共用同一版本且不能误读另一印次。权利与 OCR/页码核验完成后，把获准原书放入受控对象存储，建立全文与 pgvector 索引并通过 MCP 返回证据引用。用网页模拟设备采集；内部可用 SQLAdmin 查看，岛主通过受控页面或 API 确认发布。拒绝或撤回后公开页面不得继续披露。
3. 部署岛主云端 Agent 的受限管家能力；教师 Agent 经 MCP 调用绑定租户身份的白名单工具，只允许读取本岛获准资料，验收答复、拒绝、待审批、云端故障恢复、请求限额和用量归属。先用模拟访客请求完成联调。
4. 在现有 Web 岛接入获准空间清单与管家入口，完成登岛、探索物件、提问、留资或报名中的一条完整动线；记录访问、互动和来源可追溯的岛主提醒。首期只做与教培业务目标相关的两三套轻量互动逻辑。
5. 用 ESP32-S3 实物调用同一设备 API，验收采集、上传、回执、断网重试、绑定撤销和重复请求去重。首期硬件作为控制与采集终端，不承担 Agent 推理或长期资料存储；缺失的摄像头/触控能力由手机或网页补充并修订范围。
6. Web 与硬件闭环稳定后，接入真实访客云端 Agent，发布指向审计入口的 A2A Agent Card；再扩展微信小程序和多岛屿产品。学生独立副岛、竞赛副本、复杂建造与新引擎列入二期验证。

首期成功判据：至少一份带来源的资料完成“采集 → 岛主确认 → 发布或拒绝”，公开页面只出现获准版本；一册已核准教材能被两个模拟教师 Agent 通过同一目录引用并取回正确版次/页码/证据状态，教师和学生数据中没有原书副本，错误版次及无权正文请求被拒绝；一次访客互动形成可追溯的跟进事项；设备输入与网页模拟输入得到相同业务结果，重复上传不生成重复内容。后续 Agent 交互验收要求同一 interaction_id 贯通访客入口、A2A 请求、管家决策、岛主审批、答复和提醒，并验证云端故障恢复不丢任务。


英语教师版的首个编码切片见[教师版实现切片](teacher-first-slice.md)，未来学生 Agent 的业务语义见[教师 MCP 与 A2A 契约](teacher-mcp-a2a-contract.md)。学生读写测评采用“开户监护同意记录 → 教师预授权策略 → Agent 实时题包/答案/量规 → 自动评分与批准 → 报告归档”的[运行契约](curriculum/realtime-assessment-and-audit-v0.1.md)；其中提交去重与审计事件须由数据库事务保证。

截至 2026-09-26，英语命题已形成可复用 [Agent Skill](../skills/english-assessment/SKILL.md) 与[题目生成流程](../skills/english-assessment/references/item-generation-workflow.md)。[实际开发状态](development-status.md)列出已跑通的本地 SQLite 自动评测、学生稳定 ID 与私有可核验档案、教师版 stdio MCP 工具、本地令牌保护 API、展示草稿与独立发布许可，以及严格的 [MCP/A2A 业务契约](teacher-mcp-a2a-contract.md)。MCP 减少工具参数和格式误用，却不能保证 Agent 选对动作；高影响发布只由教师受保护 API 执行。A2A 目前只有业务 DataPart 校验，未部署真正端点。生产 PostgreSQL、共享教材目录/全文与向量索引、真实教师/监护人身份网关、教师/学生页面与云端托管仍待实现。本地 258 份 PDF 只在私有研究目录，不在公开仓库或生产集群。

学生独立小岛的阶段范围尚待产品确认；技术上先预留主岛与成员关系，不把学生独立建岛列为首个纵向切片的既定交付。外购硬件的准确型号、摄像头/触屏配置和是否作为首期标配，也在实物测试与商业验证后冻结。

## 8. 协议开源、云端托管与运营边界

### 决策与范围

Hyper Dimension 可以公开业务协议，也可以开源云端后端代码。前提是商业优势来自让用户持续获得建岛、被发现、可信交互和经营结果的服务，而不是限制别人读取代码。开放协议使第三方 Agent 能按共同语义接入；A2A 已负责 Agent Card、消息和任务，Hyper Dimension 需定义资料、授权、发布、审批、审计、岛屿关系和访客动作的业务 schema 与状态语义。[A2A 规范](https://a2a-protocol.org/v1.0.0/specification/)

| 可公开的交付物 | 平台持续运营的能力或必须隔离的数据 |
| --- | --- |
| 业务协议、schema、API 规范与兼容性用例 | 岛屿发现、流量分发、创作者与访客社区运营 |
| A2A 扩展、SDK、2D/3D 建岛包及参考后端 | 托管、升级、稳定性、客服、内容服务与硬件接入支持 |
| 审计入口、云端 Agent 运行与权限执行代码（成熟后可开源） | 用户资料、授权记录、交互正文、运营数据、密钥和生产配置 |

代码公开不等于业务数据公开。开源仓库只放样例数据与无密钥配置；生产数据库、真实素材、客户资料、模型凭据、签名密钥、日志和备份必须留在受控环境。素材与 3D 模型的许可逐项核对，不能因为代码开源就默认拥有转授权权利。商标、域名和品牌授权也应单独管理。

### 发布顺序与许可边界

1. **首期先公开协议草案与建岛包**：定义对象和事件版本，提供示例、SDK/Skill 调用方式与兼容性测试；先用教培样板修正语义，再标记稳定版本。
2. **业务闭环验证后公开参考后端**：让第三方能在云端部署一座岛并接入 A2A，同时保留官方托管为省心的默认体验；参考实现和生产环境执行相同的权限与审计语义。
3. **生产后端成熟后评估整体开源**：依据安全审查、依赖与素材许可、部署文档、运维负担及商业验证决定范围和许可证。开源不要求公布生产密钥、用户数据或私有运营配置。

若采用符合开源定义的许可证，必须接受他人复制、修改、重新部署及提供竞争服务的可能；以“禁止商业使用”限制竞争者的源码许可不能按通常定义称为开源。[OSI 开源定义](https://opensource.org/osd)、[OSI 常见问题](https://opensource.org/faq) 具体许可证依各仓库的 LICENSE 与依赖许可确定；本仓库已采用 MIT。开源后的官方服务可对托管、运营支持和模型用量收费；收费规则、用户自带模型凭据和额度边界应清晰。GitLab 的开源核心与付费订阅说明证明这种组合在其他产品中存在，但不构成本项目商业可行性的证据。[GitLab 官方说明](https://handbook.gitlab.com/handbook/company/stewardship/)

### 首期要验证的运营优势

第一个样板应记录：从拿到建岛包到发布获准内容的时间与完成率、每岛真实访客及跨岛互动、访客复访、留资或报名等目标动作完成率、岛主持续更新率，以及用户选择官方云端托管或运营服务的意愿。若用户拿到同样的代码后仍愿意选择官方服务，且参与者增多能改善发现、互动和复访，才说明运营优势开始形成。仅有安装量或 GitHub 关注量不足以证明护城河。

## 9. 为二期交互体验保留的接口与引擎选择

二期交互体验方向包括可探索物件、角色化 Agent、访客任务动线与成长反馈；闭环可按“登岛 → 发现物件 → 与 Agent 交谈 → 完成主要动作 → 岛主更新 → 复访感知变化”验证。岛屿主题、区域、物件、Agent 角色与成长状态应版本化。二期具体功能与引擎尚未定稿。

首期接管现有 Astro prototype 并实现管家对话时，应预留以下与渲染引擎无关的契约：

1. 空间清单：为岛屿、场景、区域、可交互物件及资产分配稳定 ID 和版本；物件记录内容引用、可见范围、可触发动作及状态。页面与未来引擎读取同一份空间数据，避免把业务内容只写进 GLB 或前端代码。
2. 交互事件：从首期就统一会话 ID、物件 ID、事件类型和时间戳。至少能区分登岛、物件点击、管家交流、经营动作和复访；审计与经营分析复用同一事件关联 ID，但按不同权限读取。
3. Agent 与业务接口：管家对话、资料授权、线索、提醒和岛屿成长状态由后端服务管理。渲染层只发送“访客与哪个物件/角色发生了什么交互”，接收获准展示的状态和结果。
4. 资产交付：保存 3D 源文件、GLB、许可、版本和性能指标，并保留 2D/2.5D 展示路径。二期换引擎时迁移资产和配置，而不是从线上压缩脚本反向恢复业务逻辑。

二期可以比较以下引擎，当前不锁定：

| 候选 | 浏览器交互方式 | 对当前原型的影响 |
| --- | --- | --- |
| 现有 Web/Three.js | 在 Astro 页面内渐进增强 | 作为加载、移动端与开发成本的比较基线 |
| [Godot](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html) | 可导出 Web 项目；浏览器需支持 WebAssembly 和 WebGL 2.0 | 可在独立体验区域接入；Godot 为 [MIT 开源许可](https://godotengine.org/license/)，Web 导出及移动端性能需实测 |
| [Unity Web](https://docs.unity.com/engine/6000.7/manual/platform-specific/webgl) | 构建 Web 应用并由页面承载 | 适合比较成熟交互工具链；须核算包体、移动端体验及商业许可 |
| [Unreal Engine](https://dev.epicgames.com/documentation/unreal-engine/pixel-streaming-in-unreal-engine) | 若继续以浏览器访问，可评估在 GPU 服务器运行场景并用 Pixel Streaming 推送到网页 | 适合验证高保真场景，但需要独立 GPU 与流媒体运维；当前静态站点机不承载该运行时，且 UE 采用 [Epic 专有许可](https://www.unrealengine.com/eula/unreal) |

引擎决策应使用同一个岛屿样例、相同物件与 Agent 接口做小范围验证，比较首屏时间、移动端兼容性、交互延迟、视觉需求、资产制作工时、服务器成本和许可条件。二期无论使用哪种引擎，现有 Astro 站点都可以保留为入口、账户和内容层；引擎承担空间呈现与操作，不掌管身份、授权、审计和 Agent 任务真相源。

相关实现状态见[开发状态](development-status.md)，教材索引设计见[共享教材库与向量索引](curriculum/shared-textbook-catalog-v0.1.md)。
